# Vigil technical notes

## Layout

One plugin, `isimp.Vigil`. `src/VigilPlugin.cs` is the host: it starts the switched-on areas (a dedicated server runs only the recorder), passes them Unity's calls, and answers the `vigil` console command. `src/Host` holds the panel (IMGUI, `Ui` blocks and `Skin`), the HUD line, the link to the server and the module base. `src/Recorder`, `src/Spawns` and `src/Cleanup` are the areas. `src/Core` holds everything that needs no game; `tests/Vigil.Tests` tests it on its own. The version is set only in `Vigil.csproj`.

## Files

`Vigil-timeline.tsv` has a row per second; `Vigil-incident-*.txt` are reports, `Vigil-events.tsv` lists joins, leaves, saves, weather changes and spawns, `Vigil-peers.tsv` (server) has a row per player per second, and `Vigil-summary.txt` sums up the session. `Vigil-state/` is never archived: the hook journal and skip list (a hook that crashed the game is skipped from the next start), `session.running` (present while running, touched once a minute, so a crash is noticed), panel state, and on a server `alerts.tsv` and `online.txt`. At start the previous session moves to `Vigil-runs/`.

## Timing

Mods' Unity callbacks and coroutines are timed with a Harmony prefix and finalizer, on the main thread only. A deep capture (on a slow stretch or `vigil deep`) times every game method mods patch, installed a few per frame. After 2 s it splits the 25 costliest (and any that stalls a frame later) into the game's code and the mods' share, and then times each mod's prefix, postfix and finalizer on those methods by itself (`Core/Recorder/PatchTime`), the timers' own cost per call taken off: the report's first by-mod section gives each mod's own patch code per frame with its costliest patch, and lists the mods whose transpilers change the game's code, which can only be timed inside those methods. A patch the runtime folded into the game's method escapes its own timer. The older by-mod section, which gives every mod patching a method that method's whole time, follows it. Leaving the world ends a deep capture at once (`Core/Recorder/DeepPlan.OnLeaving`): a prefix on `ZNet.StopAll` on any game but a dedicated server marks the leave, and at the next frame a capture that is measuring writes its report with what it has (it says it ended early) and every deep timer comes out in that frame (`PhaseTimer.RemoveDeepNow`, `BudgetedQueue.Drain`), counted as Vigil's own time; `Vigil-events.tsv` gets a `deep` line with the timers and what taking them out took. Taken out a few per frame, as at the end of a normal capture, they would keep the capture and the recording going for minutes in the main menu, where frames are long. Quitting the game has no next frame and takes nothing out. The self-test times one other mod's patch on a game method that runs every frame for 2 s. Vigil's own calls cannot be hooked, since the recorder closes each frame inside its own Update, so the plugin times them itself and reports them as the mod Vigil.

Incoming network messages are timed per kind through the game's two dispatch methods (`src/Recorder/HandlerTime.cs`) while recording, and on a server also from a player's connection until the game takes them in (`ProbeState.Joining`), since a join's costliest messages often arrive in the frame of the connection itself, before recording, switched on at the next frame, would see them. The auto switch counts a player still joining as a player (`RecordingPolicy.Players`). A report's sections for the current 10 s window read the window in progress. The window ends by the real clock, but the game tells a frame's length on the frame after it, which is when a hitch report is taken, so a window due in a long frame waits that frame out (`Core/Recorder/ReportWindow`); the session summary reads the window without ending it, and a pause in recording writes the window in progress as its own.

Unity's own physics step runs after the scripts' FixedUpdate in each fixed step, where no Harmony hook reaches. `src/Recorder/PhysicsStep.cs` puts two markers of its own into Unity's player loop right before and after `FixedUpdate.PhysicsFixedUpdate` on the first frame (`Hooks.PhysicsStep`, under the hook journal), two timestamps a step: the timeline's `physics_ms` (per frame, averaged over the second), the frames table of a hitch report, and the hitch explanation, which names the physics engine with its steps and leaves it out of the time outside the timed code (`Core/Recorder/HitchAnalysis`). A later change of the player loop by anything else would drop the markers; the timer then counts nothing and the census's self-test says so.

## Census

`vigil census [radius]` and the Tools tab's *Count objects* run `src/Recorder/CensusRun.cs` over several frames, about 4 ms of each: the loaded world objects within the radius of the player (renderers with their layer, distance from the camera, shadow casting, Unity's `isVisible`, instancing of their shared materials and the mesh and materials they draw; particle systems with their culling mode, main-camera frustum test, `isVisible` and live particles, and whether the object is a building piece; lights as they are after the game's `LightLod`, and whether its distance rule (`m_lightLod`), which the game's point-light cap counts, governs them; characters with their owner, tame state, AI sleep and body; other objects with a `ZSyncTransform`), objects past the radius count only with their shadow casters within the shadow distance from the camera, so the per-layer estimate covers the whole shadow distance; then in a frame of its own the scene's renderers of no world object (the same rule past the radius), then the shadow casters within each shadow-casting light's range. It then puts timers of its own (Harmony id `isimp.Vigil.census`, one method a frame, under the hook journal) on `Character.CustomFixedUpdate`, `Humanoid.CustomFixedUpdate`, `ZSyncTransform.CustomFixedUpdate`, `AnimalAI.UpdateAI` and `MonoUpdaters.FixedUpdate`, sums each instance's time for 5 s (a humanoid's own method holds its base call, so a character counts the outermost), and takes them off again. `MonsterAI.UpdateAI` carries another mod's transpiler, and a timer put on it during play would build it through that transpiler again, so monsters' AI stays out. `Core/Recorder/BaseCensus` adds it all up and writes `Vigil-census-<time>.txt`, each section led by its finding: characters' time a step and share of the game's loop, shadow casters past per-layer sun shadow distances (ShadowTrim's defaults: piece 60, piece_nonsolid 40, Default_small 30, item 25 m), renderers without instancing whose mesh and material repeat, building particle systems set to always simulate and out of view, lights with shadows against the game's caps. `Core/Recorder/Census` keeps the per-type and per-mod tables (`.tsv`, `-mods.tsv`) and the panel's result, which leads with the four findings in short lines (`BaseCensus.Findings`), the shadow and particle lines marked when they found something to change. The census counts as one of Vigil's tools in its own cost, and only one runs at a time. The self-test runs one within 16 m with 2 s of timing and checks that the report is written, the timers are out again, the characters' time does not exceed the loop that runs them, and the physics markers counted the steps.

## Vigil's own cost

The Health tab's *Vigil's own cost* card and the top of the summary add up what Vigil itself takes (`Core/Host/OwnCost`, `src/Recorder/OwnHooks.cs`, `RecorderModule.OwnCost.cs`): its own loops each frame (its areas' calls and the recorder's frame work), the panel's drawing per frame it is open, its always-on timers on the mods' callbacks (their calls times one timer pair's cost), and its hooks in the game's methods. The hooks run on hot paths (every object sent, every package, every name hashed), so they are timed only for 10 s at a time: two minutes into a session on its own and whenever *Measure* is pressed, each of Vigil's prefix, postfix and finalizer methods gets a timing prefix and finalizer, put in and taken off a few per frame under the hook journal, and the timers' own cost per call, calibrated once on an empty method, is taken off. A hook the runtime folded into the game's method escapes this and costs little. The headline is Vigil's steady work; its one-off tools are apart (`OwnTools`): the self-test (its coroutine's time over the frames it ran), deep captures (Vigil's own stepping, putting its timers in and out and writing the report, over the frames they ran; the timers' effect inside the game's methods is not in it) and the reports taken (their time on the game's thread each), and a session line spreads them over every frame. The card also gives Vigil's time on threads of its own, the size of this session's recordings per minute and its own network messages; memory per mod is not something the game's runtime tells.

## Message names

The game names a message by the hash of its name, so a package or a routed message carries only the number. Vigil names the numbers from a book (`Core/Recorder/MessageNames`), best source first: names hashed while the game runs (a postfix on the game's hash function, `StringExtensionMethods.GetStableHashCode`, hands every name to the book, names put together at run time included), each mod's config sync message (`id ConfigSync`, as ServerSync names it), and the texts in the game's and the mods' files, read once every plugin has loaded (the value names the inspector uses). A message no handler on this machine explains, such as one the server routes between players, belongs to the mod whose code holds its name. A name hashed only before Vigil loaded, and never in a file, stays `message N`, still with its mod when its handler is here. A name new to the book once the game is in a world gets the mod that hashed it: one look at the call stack for the first mod's code on the way (Vigil's and the game's own frames skipped; none is the game), at most 2,000 looks a minute, past which a name is learned without an owner. Where no file ties a name to one mod, messages and object values take that owner; a library mod hashing for another counts as itself. The summary's network part and the self-test say how many kinds of message seen were named, and from where.

## World-object data by mod

A capture of what this game sends (`Core/Recorder/ObjectData`, `src/Recorder/ObjectCapture.cs`) runs on request for 60 s from the Network tab's *World-object data by mod* card and on its own for as long as a deep capture runs. For every object sent (`ZDO.Serialize` into the upload) it reads the object's stored values (`ZDOExtraData.GetData`) and gives each value's bytes as the game writes them (`ValueSize`: a 4-byte name and the value) to whoever's code holds its name (`ValueNames`, the game first; else the mod that hashed it while playing; values with neither are unknown); the game's share is the rest of the object's data: its own values, the prefab, flags and rotation. The position and owner the game adds to every object in the upload are left out. Postfixes on the value setters of `ZDOExtraData`, which say whether a value changed, and a prefix and postfix on `ZDO.SetPosition` and `ZDO.SetRotation`, comparing the object's change counter, count which values changed on objects this game runs, which is what makes them send again; a moving object sends again for its movement whatever the mods do. The hooks stay in and count only while a capture runs. The card and the summary list the kinds that sent the most bytes and the values that changed the most; the self-test captures 3 s and checks that no kind's values add up to more than the objects sent.

## Steady messages

Every routed message a machine starts or receives is counted per mod, message and sender in the traffic report's 10 s windows (`Core/Recorder/SteadyMessages`, fed by `RpcProbe`); one the server only passes on between players keeps its sender and is counted once, where it came in. A sender is steady once it has been looked at for a minute and its rate per window over the last 12 minutes swings by no more than half its mean, the windows without it counting as nothing, which with an even rate means it comes in at least 4 of 5 windows. The server's admins see the server's list per player in the Network tab's *Steady messages, per player* card (asked every 30 s while drawn, capability `steady`), and every machine's summary lists its own. It cannot tell whether a mod needs to send so often.

## Join packages of Drop That and Spawn That

Both mods register an RPC that a joining player calls (`RPC_RequestConfigsDropThat`, `RPC_RequestConfigsSpawnThat`), whose handler builds every config package from scratch on the server's main loop: Drop That runs each `SyncManager.PackageHandlers` packer, `IMessage.Initialize`, `SplitMessageManager.Pack` (serialize, compress, split at 100 kB under a new transfer id) and serializes each split with its `BinaryFormatter` into its `OutgoingMessageService.SocketQueues`; Spawn That runs each packer (`CompressedPackage.Pack`) into `DataTransferService.Service.AddToQueue`. Both send the whole location list of the world, and measured 0.7 to 0.9 s each per join. A prefix on each handler (`src/Recorder/JoinPackagesPatch.cs`, `Core/Recorder/JoinPackages`) queues kept bytes in the same order and form instead, building them the first time; they are kept for a stamp of the world session (`ZNet` instance), the world's location count and Drop That's reloads (`SyncManager.SyncConfigs`, run by `dropthat:reload`). Neither mod reads its config files again on its own. Drop That's players get the same transfer id from each build; a joining game clears its transfer list when it loads a world, so the id is new to it. A dedicated server builds what is not kept once `ZoneSystem.LocationsGenerated` has held for 60 s with no peer connected, at most every five minutes; that time is a Vigil tool in *Vigil's own cost* and not a hitch. Every part used is looked up by name on the first frame (the mods may load after Vigil); a missing one, or a build or queueing that throws, leaves that mod to build its own, with the reason in the log and the summary. The self-test builds each mod's packages twice on the player's game and compares them (Drop That's split contents, its transfer ids aside). The switch is one of the game patches below (`Patches.JoinPackages`); the tab's *On this game* names the versions found, and *On the server* is the server's own lines, carried in its status answer (`ServerStatus.JoinPackages`).

## Spawns, base arrivals and windmills

Spawns are seen at `SpawnSystem.Spawn`, `SpawnArea.SpawnOne` and `CreatureSpawner.Spawn`, after every other mod's prefixes. The game never spawns inside a base area unless the entry allows it, so once a second the creatures hostile to the player (`BaseAI.IsEnemy`) that stand inside a base area within 100 m are noted, each once, with the base's piece and builder and the spawn's record when this game made it (`Core/Recorder/BaseArrivals`). A windmill's wind check casts the game's own 17 cover rays (`Cover.GetCoverForPoint`, from the propeller, 29.5 m each) and names what each blocked ray hits; output is (1 - cover) times the wind, none under 10 % (`Windmill.GetPowerOutput`, `Core/Recorder/BaseArrivals.cs` `WindCheck`).

## Objects with rules of their own

`src/Recorder/ObjectParts.cs` reads, for the inspector, the objects the game judges by their surroundings, and `Core/Recorder/ObjectRules` puts each in words (assembly_valheim 1.0.20). Cover is the share of the 17 rays `Cover.GetCoverForPoint` casts that hit something (`ObjectParts.CastCover` casts the same rays and names what each hits). A fermenter needs 70 % cover and a roof, checked every 10 s, or its owner restarts the batch; a beehive works under its `m_maxCover`, in its biome and, unless set otherwise, by daylight; a crop needs its biome, cultivated ground where asked, warmth (a shield generator in the Ashlands, Mountain and Deep North), nothing solid straight above within 100 m and nothing in its grow radius but unhealthy plants (and, for a plant with a vine radius, no vine within it), and grows when its own seeded time is up, withering then if its kind does when it cannot; a smelter stops without fuel, ore, a roof where it needs one, or when its smoke vent is blocked; a wet fire only burns low, a blocked one (terrain above, something solid just above, or blocked smoke) goes out; taming goes on only while the creature is fed and calm; breeding needs a ready partner within 3 m and fewer than its limit of its kind and their young within 10 m. Private values are read by reflection. The *World* tab's *Rested and comfort* card reads where the player stands: shelter is 80 % cover from the character's centre and a roof, and comfort counts only in shelter, the best piece of each comfort group within 10 m, one of each name; it is compared with the game's own count, which a mod may change.

## Weather

No game sends its weather to another: each rolls it from the world's time, once a period of `EnvMan.m_environmentDuration` seconds seeded by the period's number, from the list of the biome it is in, after the game's own overrides (a dev command, the intro, a raid, a special area, a world event, a dungeon's `EnvZone`). The server's weather (`Weather.ServerWeather`, `src/Recorder/ServerWeatherPatch.cs`, `Core/Recorder/ServerWeather`) is a config entry the server keeps and ServerSync passes on, changed by its admins (or the world's host) in the World tab or with `vigil weather set|freeze|back`, so every game running Vigil follows it and a game without Vigil keeps its own roll. A postfix on `EnvMan.GetEnvironmentOverride` gives a set weather where the game's own overrides give none. A freeze keeps one world second: a prefix on `EnvMan.UpdateEnvironment` rolls for it, so each biome keeps the weather it had then, and around `EnvMan.FixedUpdate` the game's own time-of-day switch holds that second's hour (unless the admin drew another on their own game), put back in a finalizer so nothing outside the update sees it. The game's day and night rules read the drawn hour, so a frozen hour also decides night spawns and daylight. Beds (`EnvMan.CalculateCanSleep`) and the server's check that everyone sleeps (`Game.UpdateSleeping`) go by the world's real clock while a freeze holds, and when the server skips to the morning (`EnvMan.SkipToMorning`) the freeze ends; a set weather stays. The world's time is never changed. The card's cause says who set or froze it, when in world days and hours, and what the game's own roll would give now.

## Self-test trials

Beside reading each feature once, the self-test holds Vigil's readings and changes against the game itself, on the player's game only (`src/Recorder/RecorderModule.Trials.cs`, `Core/Recorder/RuleAgreement`, `WeatherTrial`). Within 30 m, Vigil's 17 cover rays are compared with the game's `Cover.GetCoverForPoint` at each fermenter, beehive and fire, a beehive's space with its `HaveFreeSpace`, a crop's ray up and what stands in its way with the crop's status, and a smelter's vent blocker with its blocked smoke; the comfort where the player stands is compared with `Player.GetComfortLevel`. The cover and a beehive's space are read the same moment, so a difference fails; the game checks crops and smoke every few seconds, so a difference there warns, and a different comfort warns as a mod may change it. With no server's weather in charge, the roll Vigil works out is compared with the game's, and the server's weather is tried on this game for a few seconds: another weather set (or the game's own override kept, inside a dungeon), a freeze an hour of the game's day back (the hour drawn held, beds on the real clock, the roll held), then back. OdinOnDemand's level is compared with master x music for every loaded player, an opened cog panel's slider with the music slider's range, value and label, and a music volume tried from the slider and put back unsaved. A map pin is made and taken back, and the recordings folder's path copied and read back, the clipboard restored. A weather or music trial ends on its own when its seconds run out (`ServerWeatherPatch.Try`, `OdinVolumePatch.TrialTick`), as the self-test leaves a routine that runs over its time without finishing it.

## Game patches

Vigil's own game patches are switched by the server: each is a config entry under `Patches` that ServerSync passes to every player running Vigil, off unless set, changed in game by the server's admins (or the world's host) in the *Patches* tab, the server keeping the change. Each finds the code it works on by name on a player's game's first frame, when every plugin has loaded, and steps aside with the reason when an update changed it. Besides *Join packages built once* (`Patches.JoinPackages`, described above): *OdinOnDemand follows the game's volume* (`Patches.OdinOnDemandVolume`, `src/Recorder/OdinVolumePatch.cs`, `Core/Host/OdinVolume`): Valheim applies master volume inside its own mixers and to its music, and keeps the listener at 1; OdinOnDemand plays through mixers of its own and every second sets each one's `MasterVolume` to its own level, so the game's volume never reaches it. A postfix on its `BasePlayer.UpdateChecks` sets that level to 20 log10(master x music) dB (down to -80 dB); turned off, OdinOnDemand sets its own level again the next second. OdinOnDemand's master volume (a dB offset per kind of player, -15 to 15, in its config) becomes the game's music volume: its cog panel is built once and puts the master volume on its slider each time it opens (`UIController.ToggleSettingsPanel`); a postfix after that gives the slider the game's 0 to 1 range, the music volume and the label "Music Volume N %", or OdinOnDemand's own range, value and label back once the patch is off. Unity's slider reports a value its new range clamps as a change, so the slider's handler `OnMasterVolumeChanged` is skipped while Vigil sets it. Moved by the player, the handler is skipped too and the music volume set instead, as Valheim's own slider sets it (`PlatformPrefs` `MusicVolume`, `MusicMan.m_masterMusicVolume` = master x music); Valheim saves its preferences only when its settings menu applies them, so Vigil saves them once the slider has rested a second, or when the panel closes. OdinOnDemand's own master volumes stay in its config, untouched, for when the patch is off. A panel open while the switch changes catches up when it next opens. AzuMiscPatches' mute in background gives the listener back at the master volume, which then counts twice for the game's own sounds; a postfix on `EventSystem.OnApplicationFocus` after it puts the listener back at 1. Until OdinOnDemand's first update a second after a player starts, it plays at its own level. *Skip winter* (`Patches.SkipWinter`, `src/Recorder/SkipWinterPatch.cs`, `Core/Host/SeasonSkip`): Seasonality picks the next season in its next-season rule (`Core/Host/SeasonRule`): from 3.8.5 `SeasonTime.GetNextSeason()`, which reads the season under way from `SeasonTime.m_currentSeason`, called on every game when the season's time is up, the server's season reaching the others every 2 s; up to 3.8.4 `SeasonalTimer.GetNextSeason(Season)`, called only where the season changes (the dedicated server, or a game hosting its world). A postfix after every other mod's turns winter into spring while the switch is on. Seasonality's season type is unknown to Vigil, so the postfix takes the result as an object and writes the season back by name; right after hooking, Vigil asks for the season after fall and steps aside, with the reason, unless it is spring. A season set by hand is left alone. The patch is hooked on the server too.

## Startup timeline and bundle cache

`Vigil.Preloader.dll` is a BepInEx patcher (`src/Preloader`, with the rules in `src/Core/Startup`, which `tests/Vigil.Tests` covers). BepInEx runs every patcher's `Initialize` before it reads `TargetDLLs`, then edits the named assemblies and loads them; the patcher touches no Unity type before that, since an assembly loaded early can no longer be edited.

**Timeline.** `Initialize` reads the `Startup` section of `isimp.Vigil.cfg` (a read-only `ConfigFile`, never saved) and adds a BepInEx log listener. The listener keeps, with the time on a stopwatch started there, each line `StartupLines.Classify` marks: `Loading [Name Version] (GUID)` and `Chainloader startup complete` from BepInEx, `Batch-patched N methods after ... in M ms` from StartupAccelerator. BepInEx's preloader removes only its own listener when it ends and the chainloader adds its own without clearing others, so the listener hears the whole plugin load. Every other line, BepInEx's and the game's (BepInEx relays Unity's log), is kept too as a `log` step, `source: first line` cut to 160 characters, at most 6,000 a start, until the menu shows. The first step holds the milliseconds from the process start to `Initialize`. Vigil reads the steps through `Vigil.Startup.Bridge`, found by name among the loaded assemblies (`src/Recorder/StartupBridge.cs`), so `Vigil.dll` loads without the patcher. It adds `menu-scene` (a postfix on `FejdStartup.Awake`), `menu` (`FejdStartup.Start`), `menu-shown` (the next frame), on a dedicated server `world-up` (the first frame with `ZNet` and `ZoneSystem`), and per join `join-start` (`ZNet.OnNewConnection` on a player's game), `join-step` (`ZNet.RPC_PeerInfo`, from the join-step timer), `join-message` (any message handled in 100 ms or more meanwhile) and `join-world` (the first frame in the world). `StartupTimeline.Build` reads the steps: a plugin runs to the next plugin's line, the last to the chainloader's line; StartupAccelerator's batch between the chainloader's end and the menu scene is its own step; the menu takes the rest. The listener comes off once the menu shows. Between neighbouring steps and log lines up to the menu, each wait of 2 s or more is a quiet stretch (`StartupTimeline.Gaps`), named by what was starting then (the plugin, "BepInEx and patchers", "after the plugins", "the menu") and the lines either side; the report lists the ten longest. A patch batch logs only when it ends, with how long it took, so a stretch at least half inside that time is named "patching". Vigil times its own start (`StartSteps`): each step from Awake on, and the first frame's work, goes into the report as a `vigil-step`, `name|ms`.

`Vigil-startup.txt`: a header, the patcher's state, the summary, the bundle line, the join line, then every plugin slowest first with its bundles. `Vigil-startup.tsv`: one step a line, `ms`, `kind`, `text`; a `bundle` step's text is `outcome|bytes|ms|key`, with the outcome `copy`, `usual` (loaded as before, a copy is made), `plain` (not LZMA, or under 1 MB), `blocked` (its copy was refused earlier) or `failed` (its copy was refused in this load).

Vigil looks up types by name with `TypeLookup`, which asks each loaded assembly for the one full name (`Assembly.GetType`) and keeps the answer; Harmony's `AccessTools.TypeByName` lists every type of every assembly on each call and, for a name not found, logs a warning for each assembly holding a type that cannot load.

**The edit.** `Patch` gets `UnityEngine.AssetBundleModule` when the cache is on. Unity's public loads from memory and streams all end in `AssetBundle.LoadFromMemory_Internal`, `LoadFromMemoryAsync_Internal`, `LoadFromStreamInternal` and `LoadFromStreamAsyncInternal`; `BundleHookEdit` puts at the start of each `if (BundleHook.TryX(args..., out var result)) return result;`, referring to the hook by assembly and type name, and leaves the rest of the body as it was. If any of the four is missing or has another signature, nothing is edited and the reason is logged. Loads from files are not touched: the game streams its own LZ4 bundles through them.

**The hook.** `BundleHook` reads the bundle's header and block table (`BundleFormat`: UnityFS 6 to 8; Unity packs the table with LZ4 even when the blocks are LZMA, so the blocks' own flags tell) and computes its key (`BundleKey`: length, FNV-1a of the first and last MB, the Unity version). `BundleCache.Choose`: a load with a CRC asked for, a stream that cannot seek, a bundle under 1 MB, one without LZMA blocks or one whose copy was refused loads as usual; one with a ready copy loads from it; otherwise it loads as usual and gets a copy made, once a session. Vigil's own loads set a thread flag so the edited methods do not ask again, and the usual load is the public method the mod called with the same arguments. A copy is loaded with `LoadFromFile`, its asset names (`AssetsSignature`: count and hash, any order) compared with the original's; a copy that is null or differs is unloaded, refused for good, and the bundle loads as usual in the same call. A waiting load uses only a copy whose original's assets are known, and checks it when it completes. A copy is made by writing the bundle to `<key>.src` and calling `AssetBundle.RecompressAssetBundleAsync(src, tmp, BuildCompression.LZ4Runtime, 0, ThreadPriority.Low)`; once it reports success and the result reads as a UnityFS bundle with no LZMA blocks, `<key>.tmp` becomes `<key>.bundle`.

**The cache folder** is `BepInEx/cache/Vigil/bundles`: `<key>.bundle` copies and `index.tsv` (`key`, `last_used_utc`, `packed_bytes`, `copy_bytes`, `state` ready or blocked, `assets`, `plugin`). Before the first load of a start (`BundleCache.Housekeep`): a `reset` file empties the folder; otherwise copies unused for `Startup.BundleCacheKeepDays` days, copies the index does not know, and leftover `.tmp` and `.src` files go; a refused bundle stays remembered for the same days. File times of the copies are never changed, as Unity stops reading a bundle file whose time changes while it is open. The index is written to `index.tsv.new` and then moved over the old one.

**Config saves.** BepInEx 5.4's `ConfigFile.Bind` saves the whole file whenever `SaveOnConfigSet` is on (the default), and so does setting a new entry's first value; `Save` writes every setting and every line read from disk. StartupAccelerator's *Delay Config Save* turns `SaveOnConfigSet` off in a postfix on the constructor and saves once in a prefix of `FejdStartup.Awake`, but forgets a file whose mod sets `SaveOnConfigSet` itself, and a mod binding in `FejdStartup.Awake` comes after it. With `Startup.HoldConfigSaves` (a player's game) or `Startup.HoldConfigSavesOnServer`, `Initialize` puts Harmony prefixes (`ConfigSaveHook`, `isimp.Vigil.configsaves`, first in order) on `ConfigFile.Save`, `ConfigFile.Reload` and the `ConfigFile(string, bool, BepInPlugin)` constructor, before the chainloader, so StartupAccelerator's holding back of patches does not reach them. `SaveHold`: a save while holding notes the path's settings object, its plugin's name and the file's size and write time then, and BepInEx's save is skipped. Before a reload, or another settings object opening the path (the constructor reads a file that exists), the path's held save is written first, unless the file's size or write time changed after that save (a mod wrote it itself), whose write then stands. At the end each path's last held save is written, in the order of the saves, unless the file was written from outside after it. The end comes when the menu shows or a dedicated server's world is up (`RecorderModule.EndHeldSaves`, or `VigilPlugin` with the Recorder off), when the game quits, or 10 min after the hold began (at the next save, or a timer 5 s later). **The guard** covers a mod reading a settings file itself, past BepInEx. In Mono every read of a file's contents by path (`File.ReadAll*`, `File.ReadLines`, `File.OpenRead`, `StreamReader(path)`, `FileInfo.OpenRead`) ends in the internal constructor `FileStream(string path, FileMode mode, FileAccess access, FileShare share, int bufferSize, bool anonymous, FileOptions options)`, `File.Exists` in `FileSystem.FileExists`, and `File.Copy` and `FileInfo.CopyTo` in `FileSystem.CopyFile`; the hook puts prefixes on all three. An open with read access of an existing file, a check for a file, or a copy from it, of a path with a held save, writes that save first (`SaveHold.ReadPast`, which follows the same rule as a reload: a file written from outside after the save stays as written) and names the mod once per file: the first frame on the stack outside the runtime, BepInEx, Harmony and the patcher, by its plugin's name when its assembly is a plugin's. With no such frame, or with Mono's file watcher on the stack (`System.IO.DefaultWatcher`, which looks for each watched file with `File.Exists` every 750 ms on a thread of its own, and once on the mod's thread when the mod switches the watcher on), the file stays held: the watcher is not a mod reading it, and it sees the file change when the hold writes it. The watcher's own thread is then passed over at once. A quick test of the file name comes first, so other files cost a dictionary look-up. The prefixes come off when the hold ends; if they cannot go in, the hold works without them and says so. `FileInfo.Exists`, `Length` and the times, and `Directory` listings, are not covered. While the hold is on, Vigil's first frame lists the mods but leaves out the config files (their hashes would read them all); they are listed when the hold ends. Right after, each written file is read back the way `ConfigFile.Reload` reads it (`CfgValues`) and compared with its settings, which the self-test reports. The `config-saves` step's text is `why|held|files|written|flushed|ms|name=count;...|kept;...|failed;...|read past;...`. `tools/ConfigHoldProbe` runs the same settings scenarios with BepInEx's own `ConfigFile` in Valheim's Mono, without the hold and with it, and compares the files they leave byte for byte.

**Failed assembly lookups.** For an assembly not yet loaded, BepInEx's preloader resolve handler (`PreloaderRunner.LocalResolve`, the only BepInEx handler on `AppDomain.AssemblyResolve`) looks among the loaded assemblies and then runs `Utility.TryResolveDllAssembly(AssemblyName, string, out Assembly)` for BepInEx's folder, the patchers and the plugins; each lists every folder under its folder (`Directory.GetDirectories(..., AllDirectories)`) and checks each for `<name>.dll`. With `Startup.RememberFailedLookups` (a player's game) or `Startup.RememberFailedLookupsOnServer`, `Initialize` puts a prefix and a postfix (`LookupHook`, `isimp.Vigil.lookups`) on that search: a search that returned false is remembered by assembly name (without case) and folder (`LookupMemory`), and the same search is then answered false at once, until the start ends with the hold of config saves (`StartupState.ReleaseSaves`, which ends both and adds a `lookups` step: `why|answered|assemblies|name=count;...`). The look among loaded assemblies is left as it is, so an assembly loaded later is still found; a DLL put on disk during the start would not be. `tools/ConfigHoldProbe` times 40 searches for a missing assembly over 200 folders with BepInEx's own search, without and with the memory, and checks that an assembly that is there is found each time.

## Fire sounds

A player's own setting, under `Sound` in Vigil's config, shown in *Overview > Fire sounds* (`src/Recorder/RecorderModule.FireSounds.cs`, `src/Recorder/FireSoundsPatch.cs`, `Core/Host/FireSounds`). The game's fires play their loop through its sound component (`ZSFX`) on the source under the fire's enabled object: each time the loop starts it picks a level between the component's lowest and highest, fades it in, adds reverb with distance, and writes the source's volume every frame as that level times its fade, the game's concurrency factor and a modifier; `AudioMan` sorts the loops of one kind (by the component's hash) by distance to the camera every 16 frames and mutes all past the kind's cap, one more than `m_maxConcurrentSources`. The game's hearth plays at 0.4 to 0.6, fade-in 0.1 s, cap 2; its fire pit, torches and braziers at 0.6 to 1.0, cap 5 or 6. A mod's fire whose loop is a plain source plays at the source's own volume, every one of them, and a source on no mixer group is outside the game's SFX and master volume, which the game applies inside its mixer. A postfix after `Fireplace.Awake` (skipped for a placement ghost, which has no world object) lists the fire's looping sources. With `ModFiresFollowGameRules` on, a source without the component gets one with the hearth's values, the source's clip as its one clip, and a hash made from the fire's prefab name, so the game caps loops of that kind on their own; a source on no mixer group goes on the group the game's hearth plays through (or the game mixer's `SFX` group). The component's `Awake` and `Start` run as the fire lights and start the loop under its rules; switched off, a component given is removed with its play-on-awake off first, since its `OnDisable` would stop the loop, and the source's own volume comes back. `FireLevel` (0 to 100) reaches the fires `FireLevelAppliesTo` names: a loop under the rules through the component's volume modifier, which only `Character` and `Vagon` write on their own sounds, a plain loop as its own volume times the level. Both apply to the loaded loops at once; the slider moves them as it is dragged and writes the config when let go. A fire that came without the rules counts as without them for the scope even once it got them. The self-test compares each near loop's level with the setting's and gives the rules to a muted stand-in source on an object of its own, which it then destroys.

## Drops

A connection that ends without a goodbye is read from its last minute (`Core/Recorder/DropAnalysis`): traffic that faded or packets that came further apart before the silence point at the other side's game, a stop all at once at the line. Steam's incoming rate is an estimate that changes in steps of a few seconds and decays after the packets stop, so the comparison uses the seconds before the real stop: the earliest of the last second with traffic, a pause between packets growing by about a second each second, and unconfirmed data piling up from one second to the end (`DropAnalysis.StopAt`).

## The link to the server's Vigil

Four routed messages (`Vigil_Hello`, `Vigil_HelloReply`, `Vigil_Admin`, `Vigil_AdminReply`) carry one line of named values each. The hello tells each side the other's version and capabilities and whether the player is an admin. The server checks admin status for every question; sharing, spawn logs and parity are open to every player. Settings the server decides (its fog limit) go through ServerSync.

## Alerts

The server turns its incidents, shared spawn logs, shared reports and an unclean previous run into alerts, keeps a week of them in `Vigil-state/alerts.tsv`, and an admin's game asks for new ones every 10 s. Falling behind and each player's connection alert at most once in ten minutes, spawns at one base once an hour. Of the reports players share, only those sent by hand (lag and environment reports) alert; what their games share on their own is listed among the server's reports.

## Load test and player simulation

`vigil load` sends world-update traffic in rising steps between a player's game and the server, then reports what each direction carried and what held it back. `vigil load players` adds simulated players on the server in doubling steps and reports how many it kept up with. Only admins can start either, and the server refuses while other players are on unless `force` is added.

## Building

`dotnet build Vigil.csproj -c Release` builds against the installed game (the plugin itself reaches the profile and the server through Gale from Hexium); `-p:LibsDir=lib` builds against the committed reference stubs instead, as CI does. `dotnet test tests/Vigil.Tests` runs the tests. Releasing is in [releasing.md](releasing.md).
