# Vigil technical notes

## Layout

One plugin, `isimp.Vigil`. `src/VigilPlugin.cs` is the host: it starts the switched-on areas (a dedicated server runs only the recorder), passes them Unity's calls, and answers the `vigil` console command. `src/Host` holds the panel (IMGUI, `Ui` blocks and `Skin`), the HUD line, the link to the server and the module base. `src/Recorder`, `src/Spawns` and `src/Cleanup` are the areas. `src/Core` holds everything that needs no game; `tests/Vigil.Tests` tests it on its own. The version is set only in `Vigil.csproj`.

## Files

`Vigil-timeline.tsv` has a row per second; `Vigil-incident-*.txt` are reports, `Vigil-events.tsv` lists joins, leaves, saves, weather changes and spawns, `Vigil-peers.tsv` (server) has a row per player per second, and `Vigil-summary.txt` sums up the session. `Vigil-state/` is never archived: the hook journal and skip list (a hook that crashed the game is skipped from the next start), `session.running` (present while running, touched once a minute, so a crash is noticed), panel state, and on a server `alerts.tsv` and `online.txt`. At start the previous session moves to `Vigil-runs/`.

## Timing

Mods' Unity callbacks and coroutines are timed with a Harmony prefix and finalizer, on the main thread only. A deep capture (on a slow stretch or `vigil deep`) times every game method mods patch, installed a few per frame. After 2 s it splits the 25 costliest (and any that stalls a frame later) into the game's code and the mods' share, and then times each mod's prefix, postfix and finalizer on those methods by itself (`Core/Recorder/PatchTime`), the timers' own cost per call taken off: the report's first by-mod section gives each mod's own patch code per frame with its costliest patch, and lists the mods whose transpilers change the game's code, which can only be timed inside those methods. A patch the runtime folded into the game's method escapes its own timer. The older by-mod section, which gives every mod patching a method that method's whole time, follows it. The self-test times one other mod's patch on a game method that runs every frame for 2 s. Vigil's own calls cannot be hooked, since the recorder closes each frame inside its own Update, so the plugin times them itself and reports them as the mod Vigil.

Incoming network messages are timed per kind through the game's two dispatch methods (`src/Recorder/HandlerTime.cs`) while recording, and on a server also from a player's connection until the game takes them in (`ProbeState.Joining`), since a join's costliest messages often arrive in the frame of the connection itself, before recording, switched on at the next frame, would see them. The auto switch counts a player still joining as a player (`RecordingPolicy.Players`). A report's sections for the current 10 s window read the window in progress. The window ends by the real clock, but the game tells a frame's length on the frame after it, which is when a hitch report is taken, so a window due in a long frame waits that frame out (`Core/Recorder/ReportWindow`); the session summary reads the window without ending it, and a pause in recording writes the window in progress as its own.

Unity's own physics step runs after the scripts' FixedUpdate in each fixed step, where no Harmony hook reaches. `src/Recorder/PhysicsStep.cs` puts two markers of its own into Unity's player loop right before and after `FixedUpdate.PhysicsFixedUpdate` on the first frame (`Hooks.PhysicsStep`, under the hook journal), two timestamps a step: the timeline's `physics_ms` (per frame, averaged over the second), the frames table of a hitch report, and the hitch explanation, which names the physics engine with its steps and leaves it out of the time outside the timed code (`Core/Recorder/HitchAnalysis`). A later change of the player loop by anything else would drop the markers; the timer then counts nothing and the census's self-test says so.

## Census

`vigil census [radius]` and the Tools tab's *Count objects* run `src/Recorder/CensusRun.cs` over several frames, about 4 ms of each: the loaded world objects within the radius of the player (renderers with their layer, distance from the camera, shadow casting, Unity's `isVisible`, instancing of their shared materials and the mesh and materials they draw; particle systems with their culling mode, main-camera frustum test, `isVisible` and live particles, and whether the object is a building piece; lights as they are after the game's `LightLod`; characters with their owner, tame state, AI sleep and body; other objects with a `ZSyncTransform`), then in a frame of its own the scene's renderers of no world object, then the shadow casters within each shadow-casting light's range. It then puts timers of its own (Harmony id `isimp.Vigil.census`, one method a frame, under the hook journal) on `Character.CustomFixedUpdate`, `Humanoid.CustomFixedUpdate`, `ZSyncTransform.CustomFixedUpdate`, `AnimalAI.UpdateAI` and `MonoUpdaters.FixedUpdate`, sums each instance's time for 5 s (a humanoid's own method holds its base call, so a character counts the outermost), and takes them off again. `MonsterAI.UpdateAI` carries another mod's transpiler, and a timer put on it during play would build it through that transpiler again, so monsters' AI stays out. `Core/Recorder/BaseCensus` adds it all up and writes `Vigil-census-<time>.txt`, each section led by its finding: characters' time a step and share of the game's loop, shadow casters past per-layer sun shadow distances (ShadowTrim's defaults: piece 60, piece_nonsolid 40, Default_small 30, item 25 m), renderers without instancing whose mesh and material repeat, building particle systems set to always simulate and out of view, lights with shadows against the game's caps. `Core/Recorder/Census` keeps the per-type and per-mod tables (`.tsv`, `-mods.tsv`) and the panel's result, which leads with the four findings in short lines (`BaseCensus.Findings`), the shadow and particle lines marked when they found something to change. The census counts as one of Vigil's tools in its own cost, and only one runs at a time. The self-test runs one within 16 m with 2 s of timing and checks that the report is written, the timers are out again, the characters' time does not exceed the loop that runs them, and the physics markers counted the steps.

## Vigil's own cost

The Health tab's *Vigil's own cost* card and the top of the summary add up what Vigil itself takes (`Core/Host/OwnCost`, `src/Recorder/OwnHooks.cs`, `RecorderModule.OwnCost.cs`): its own loops each frame (its areas' calls and the recorder's frame work), the panel's drawing per frame it is open, its always-on timers on the mods' callbacks (their calls times one timer pair's cost), and its hooks in the game's methods. The hooks run on hot paths (every object sent, every package, every name hashed), so they are timed only for 10 s at a time: two minutes into a session on its own and whenever *Measure* is pressed, each of Vigil's prefix, postfix and finalizer methods gets a timing prefix and finalizer, put in and taken off a few per frame under the hook journal, and the timers' own cost per call, calibrated once on an empty method, is taken off. A hook the runtime folded into the game's method escapes this and costs little. The headline is Vigil's steady work; its one-off tools are apart (`OwnTools`): the self-test (its coroutine's time over the frames it ran), deep captures (Vigil's own stepping, putting its timers in and out and writing the report, over the frames they ran; the timers' effect inside the game's methods is not in it) and the reports taken (their time on the game's thread each), and a session line spreads them over every frame. The card also gives Vigil's time on threads of its own, the size of this session's recordings per minute and its own network messages; memory per mod is not something the game's runtime tells.

## Message names

The game names a message by the hash of its name, so a package or a routed message carries only the number. Vigil names the numbers from a book (`Core/Recorder/MessageNames`), best source first: names hashed while the game runs (a postfix on the game's hash function, `StringExtensionMethods.GetStableHashCode`, hands every name to the book, names put together at run time included), each mod's config sync message (`id ConfigSync`, as ServerSync names it), and the texts in the game's and the mods' files, read once every plugin has loaded (the value names the inspector uses). A message no handler on this machine explains, such as one the server routes between players, belongs to the mod whose code holds its name. A name hashed only before Vigil loaded, and never in a file, stays `message N`, still with its mod when its handler is here. A name new to the book once the game is in a world gets the mod that hashed it: one look at the call stack for the first mod's code on the way (Vigil's and the game's own frames skipped; none is the game), at most 2,000 looks a minute, past which a name is learned without an owner. Where no file ties a name to one mod, messages and object values take that owner; a library mod hashing for another counts as itself. The summary's network part and the self-test say how many kinds of message seen were named, and from where.

## World-object data by mod

A capture of what this game sends (`Core/Recorder/ObjectData`, `src/Recorder/ObjectCapture.cs`) runs on request for 60 s from the Network tab's *World-object data by mod* card and on its own for as long as a deep capture runs. For every object sent (`ZDO.Serialize` into the upload) it reads the object's stored values (`ZDOExtraData.GetData`) and gives each value's bytes as the game writes them (`ValueSize`: a 4-byte name and the value) to whoever's code holds its name (`ValueNames`, the game first; else the mod that hashed it while playing; values with neither are unknown); the game's share is the rest of the object's data: its own values, the prefab, flags and rotation. The position and owner the game adds to every object in the upload are left out. Postfixes on the value setters of `ZDOExtraData`, which say whether a value changed, and a prefix and postfix on `ZDO.SetPosition` and `ZDO.SetRotation`, comparing the object's change counter, count which values changed on objects this game runs, which is what makes them send again; a moving object sends again for its movement whatever the mods do. The hooks stay in and count only while a capture runs. The card and the summary list the kinds that sent the most bytes and the values that changed the most; the self-test captures 3 s and checks that no kind's values add up to more than the objects sent.

## Steady messages

Every routed message a machine starts or receives is counted per mod, message and sender in the traffic report's 10 s windows (`Core/Recorder/SteadyMessages`, fed by `RpcProbe`); one the server only passes on between players keeps its sender and is counted once, where it came in. A sender is steady once it has been looked at for a minute and its rate per window over the last 12 minutes swings by no more than half its mean, the windows without it counting as nothing, which with an even rate means it comes in at least 4 of 5 windows. The server's admins see the server's list per player in the Network tab's *Steady messages, per player* card (asked every 30 s while drawn, capability `steady`), and every machine's summary lists its own. It cannot tell whether a mod needs to send so often.

## Join packages of Drop That and Spawn That

Both mods register an RPC that a joining player calls (`RPC_RequestConfigsDropThat`, `RPC_RequestConfigsSpawnThat`), whose handler builds every config package from scratch on the server's main loop: Drop That runs each `SyncManager.PackageHandlers` packer, `IMessage.Initialize`, `SplitMessageManager.Pack` (serialize, compress, split at 100 kB under a new transfer id) and serializes each split with its `BinaryFormatter` into its `OutgoingMessageService.SocketQueues`; Spawn That runs each packer (`CompressedPackage.Pack`) into `DataTransferService.Service.AddToQueue`. Both send the whole location list of the world, and measured 0.7 to 0.9 s each per join. A prefix on each handler (`src/Recorder/JoinPackagesPatch.cs`, `Core/Recorder/JoinPackages`) queues kept bytes in the same order and form instead, building them the first time; they are kept for a stamp of the world session (`ZNet` instance), the world's location count and Drop That's reloads (`SyncManager.SyncConfigs`, run by `dropthat:reload`). Neither mod reads its config files again on its own. Drop That's players get the same transfer id from each build; a joining game clears its transfer list when it loads a world, so the id is new to it. A dedicated server builds what is not kept once `ZoneSystem.LocationsGenerated` has held for 60 s with no peer connected, at most every five minutes; that time is a Vigil tool in *Vigil's own cost* and not a hitch. Every part used is looked up by name on the first frame (the mods may load after Vigil); a missing one, or a build or queueing that throws, leaves that mod to build its own, with the reason in the log and the summary. The self-test builds each mod's packages twice on the player's game and compares them (Drop That's split contents, its transfer ids aside). The switch is one of the game patches below (`Patches.JoinPackages`); the tab's *On this game* names the versions found, and *On the server* is the server's own lines, carried in its status answer (`ServerStatus.JoinPackages`).

## Spawns, base arrivals and windmills

Spawns are seen at `SpawnSystem.Spawn`, `SpawnArea.SpawnOne` and `CreatureSpawner.Spawn`, after every other mod's prefixes. The game never spawns inside a base area unless the entry allows it, so once a second the creatures hostile to the player (`BaseAI.IsEnemy`) that stand inside a base area within 100 m are noted, each once, with the base's piece and builder and the spawn's record when this game made it (`Core/Recorder/BaseArrivals`). A windmill's wind check casts the game's own 17 cover rays (`Cover.GetCoverForPoint`, from the propeller, 29.5 m each) and names what each blocked ray hits; output is (1 - cover) times the wind, none under 10 % (`Windmill.GetPowerOutput`, `Core/Recorder/BaseArrivals.cs` `WindCheck`).

## Objects with rules of their own

`src/Recorder/ObjectParts.cs` reads, for the inspector, the objects the game judges by their surroundings, and `Core/Recorder/ObjectRules` puts each in words (assembly_valheim 1.0.20). Cover is the share of the 17 rays `Cover.GetCoverForPoint` casts that hit something (`ObjectParts.CastCover` casts the same rays and names what each hits). A fermenter needs 70 % cover and a roof, checked every 10 s, or its owner restarts the batch; a beehive works under its `m_maxCover`, in its biome and, unless set otherwise, by daylight; a crop needs its biome, cultivated ground where asked, warmth (a shield generator in the Ashlands, Mountain and Deep North), nothing solid straight above within 100 m and nothing in its grow radius but unhealthy plants (and, for a plant with a vine radius, no vine within it), and grows when its own seeded time is up, withering then if its kind does when it cannot; a smelter stops without fuel, ore, a roof where it needs one, or when its smoke vent is blocked; a wet fire only burns low, a blocked one (terrain above, something solid just above, or blocked smoke) goes out; taming goes on only while the creature is fed and calm; breeding needs a ready partner within 3 m and fewer than its limit of its kind and their young within 10 m. Private values are read by reflection. The *World* tab's *Rested and comfort* card reads where the player stands: shelter is 80 % cover from the character's centre and a roof, and comfort counts only in shelter, the best piece of each comfort group within 10 m, one of each name; it is compared with the game's own count, which a mod may change.

## Weather

No game sends its weather to another: each rolls it from the world's time, once a period of `EnvMan.m_environmentDuration` seconds seeded by the period's number, from the list of the biome it is in, after the game's own overrides (a dev command, the intro, a raid, a special area, a world event, a dungeon's `EnvZone`). The server's weather (`Weather.ServerWeather`, `src/Recorder/ServerWeatherPatch.cs`, `Core/Recorder/ServerWeather`) is a config entry the server keeps and ServerSync passes on, changed by its admins (or the world's host) in the World tab or with `vigil weather set|freeze|back`, so every game running Vigil follows it and a game without Vigil keeps its own roll. A postfix on `EnvMan.GetEnvironmentOverride` gives a set weather where the game's own overrides give none. A freeze keeps one world second: a prefix on `EnvMan.UpdateEnvironment` rolls for it, so each biome keeps the weather it had then, and around `EnvMan.FixedUpdate` the game's own time-of-day switch holds that second's hour (unless the admin drew another on their own game), put back in a finalizer so nothing outside the update sees it. The game's day and night rules read the drawn hour, so a frozen hour also decides night spawns and daylight. Beds (`EnvMan.CalculateCanSleep`) and the server's check that everyone sleeps (`Game.UpdateSleeping`) go by the world's real clock while a freeze holds, and when the server skips to the morning (`EnvMan.SkipToMorning`) the freeze ends; a set weather stays. The world's time is never changed. The card's cause says who set or froze it, when in world days and hours, and what the game's own roll would give now.

## Self-test trials

Beside reading each feature once, the self-test holds Vigil's readings and changes against the game itself, on the player's game only (`src/Recorder/RecorderModule.Trials.cs`, `Core/Recorder/RuleAgreement`, `WeatherTrial`). Within 30 m, Vigil's 17 cover rays are compared with the game's `Cover.GetCoverForPoint` at each fermenter, beehive and fire, a beehive's space with its `HaveFreeSpace`, a crop's ray up and what stands in its way with the crop's status, and a smelter's vent blocker with its blocked smoke; the comfort where the player stands is compared with `Player.GetComfortLevel`. The cover and a beehive's space are read the same moment, so a difference fails; the game checks crops and smoke every few seconds, so a difference there warns, and a different comfort warns as a mod may change it. With no server's weather in charge, the roll Vigil works out is compared with the game's, and the server's weather is tried on this game for a few seconds: another weather set (or the game's own override kept, inside a dungeon), a freeze an hour of the game's day back (the hour drawn held, beds on the real clock, the roll held), then back. OdinOnDemand's level is compared with master x music for every loaded player, an opened cog panel's slider with the music slider's range, value and label, and a music volume tried from the slider and put back unsaved. A map pin is made and taken back, and the recordings folder's path copied and read back, the clipboard restored. A weather or music trial ends on its own when its seconds run out (`ServerWeatherPatch.Try`, `OdinVolumePatch.TrialTick`), as the self-test leaves a routine that runs over its time without finishing it.

## Game patches

Vigil's own game patches are switched by the server: each is a config entry under `Patches` that ServerSync passes to every player running Vigil, off unless set, changed in game by the server's admins (or the world's host) in the *Patches* tab, the server keeping the change. Each finds the code it works on by name on a player's game's first frame, when every plugin has loaded, and steps aside with the reason when an update changed it. Besides *Join packages built once* (`Patches.JoinPackages`, described above): *OdinOnDemand follows the game's volume* (`Patches.OdinOnDemandVolume`, `src/Recorder/OdinVolumePatch.cs`, `Core/Host/OdinVolume`): Valheim applies master volume inside its own mixers and to its music, and keeps the listener at 1; OdinOnDemand plays through mixers of its own and every second sets each one's `MasterVolume` to its own level, so the game's volume never reaches it. A postfix on its `BasePlayer.UpdateChecks` sets that level to 20 log10(master x music) dB (down to -80 dB); turned off, OdinOnDemand sets its own level again the next second. OdinOnDemand's master volume (a dB offset per kind of player, -15 to 15, in its config) becomes the game's music volume: its cog panel is built once and puts the master volume on its slider each time it opens (`UIController.ToggleSettingsPanel`); a postfix after that gives the slider the game's 0 to 1 range, the music volume and the label "Music Volume N %", or OdinOnDemand's own range, value and label back once the patch is off. Unity's slider reports a value its new range clamps as a change, so the slider's handler `OnMasterVolumeChanged` is skipped while Vigil sets it. Moved by the player, the handler is skipped too and the music volume set instead, as Valheim's own slider sets it (`PlatformPrefs` `MusicVolume`, `MusicMan.m_masterMusicVolume` = master x music); Valheim saves its preferences only when its settings menu applies them, so Vigil saves them once the slider has rested a second, or when the panel closes. OdinOnDemand's own master volumes stay in its config, untouched, for when the patch is off. A panel open while the switch changes catches up when it next opens. AzuMiscPatches' mute in background gives the listener back at the master volume, which then counts twice for the game's own sounds; a postfix on `EventSystem.OnApplicationFocus` after it puts the listener back at 1. Until OdinOnDemand's first update a second after a player starts, it plays at its own level. *Skip winter* (`Patches.SkipWinter`, `src/Recorder/SkipWinterPatch.cs`, `Core/Host/SeasonSkip`): Seasonality (3.8.x) picks the next season in `SeasonalTimer.GetNextSeason`, called only where the season changes (the dedicated server, or a game hosting its world); a postfix after every other mod's turns winter into spring while the switch is on. Seasonality's season type is unknown to Vigil, so the postfix takes the result as an object and writes the season back by name; right after hooking, Vigil asks for the season after fall and steps aside, with the reason, unless it is spring. A season set by hand is left alone. The patch is hooked on the server too.

## Drops

A connection that ends without a goodbye is read from its last minute (`Core/Recorder/DropAnalysis`): traffic that faded or packets that came further apart before the silence point at the other side's game, a stop all at once at the line. Steam's incoming rate is an estimate that changes in steps of a few seconds and decays after the packets stop, so the comparison uses the seconds before the real stop: the earliest of the last second with traffic, a pause between packets growing by about a second each second, and unconfirmed data piling up from one second to the end (`DropAnalysis.StopAt`).

## The link to the server's Vigil

Four routed messages (`Vigil_Hello`, `Vigil_HelloReply`, `Vigil_Admin`, `Vigil_AdminReply`) carry one line of named values each. The hello tells each side the other's version and capabilities and whether the player is an admin. The server checks admin status for every question; sharing, spawn logs and parity are open to every player. Settings the server decides (its fog limit) go through ServerSync.

## Alerts

The server turns its incidents, shared spawn logs, shared reports and an unclean previous run into alerts, keeps a week of them in `Vigil-state/alerts.tsv`, and an admin's game asks for new ones every 10 s. Falling behind and each player's connection alert at most once in ten minutes, spawns at one base once an hour. Of the reports players share, only those sent by hand (lag and environment reports) alert; what their games share on their own is listed among the server's reports.

## Load test and player simulation

`vigil load` sends world-update traffic in rising steps between a player's game and the server, then reports what each direction carried and what held it back. `vigil load players` adds simulated players on the server in doubling steps and reports how many it kept up with. Only admins can start either, and the server refuses while other players are on unless `force` is added.

## Building

`dotnet build Vigil.csproj -c Release` builds against the installed game (the plugin itself reaches the profile and the server through Gale from Hexium); `-p:LibsDir=lib` builds against the committed reference stubs instead, as CI does. `dotnet test tests/Vigil.Tests` runs the tests. Releasing is in [releasing.md](releasing.md).
